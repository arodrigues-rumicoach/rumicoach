# Sign in with Apple (iOS only)

Native-flow Sign in with Apple: the iOS app obtains an identity token from
`ASAuthorizationController` (via `expo-apple-authentication`) and the backend verifies
it directly against Apple's published JWKS. **No Apple secret, Services ID, or `.p8`
key is needed for this flow** — verification is signature + issuer + audience checks
on a public-key JWT, exactly like Google ID-token validation.

**Where each moving part lives:**

| What | Where |
|---|---|
| Backend token validation | `rumi-be/internal/handlers/apple.go` → `validateAppleToken` (RS256 vs `https://appleid.apple.com/auth/keys`, `iss` = `https://appleid.apple.com`, `aud` ∈ `APPLE_CLIENT_IDS`) |
| Backend endpoints | `POST /v1/auth/apple` (login), `POST /v1/auth/verifications/sso` with `type: apple` (signup pre-check), `appleIdentityToken` on `POST /v1/auth/register` / `POST /v1/waitlist` |
| Backend env | `APPLE_CLIENT_IDS` (falls back to `APPLE_CLIENT_ID`; comma-separated bundle IDs). **Default already covers `coach.rumi.app,coach.rumi.app.qa`** — no infra change needed unless the bundle IDs change |
| Identity storage | `models.Identity.AppleID` (unique, auth DB) = the token's stable `sub` claim |
| Mobile capability | `rumi-mobile`: `expo-apple-authentication` plugin in `app.json`; entitlement `com.apple.developer.applesignin` in `ios/Rumi/Rumi.entitlements` (generated by prebuild — don't hand-edit) |
| Mobile UI/flow | `app/(auth)/signin.tsx` (`handleAppleLogin`), `src/hooks/useSignupForm.ts` (`handleAppleLogin` → SSO pre-check → register), both gated `Platform.OS === 'ios'` |

## Console work (one-time, per app)

In the [Apple Developer portal](https://developer.apple.com/account) → Identifiers,
enable the **Sign in with Apple** capability on both App IDs (`coach.rumi.app` and
`coach.rumi.app.qa`). That's all: the native flow needs no Services ID, key, or
redirect URL. Xcode/EAS picks up the entitlement from the app's provisioning profile
on the next build.

## Behavior and invariants

- **The `sub` claim is the account key.** Apple only guarantees the user's **name on
  the very first authorization** (delivered client-side, never inside the token), and
  with "Hide My Email" the token's email is a per-app `@privaterelay.appleid.com`
  address. All lookups go `apple_id` first; the email is a fallback link for accounts
  that predate Apple sign-in, and only the **verified in-token email** may link —
  the client-supplied `email`/`name` fields on `/auth/apple` are informational.
- **Login never creates accounts** (mirrors Google): unknown Apple user → 403
  `ACCOUNT_NOT_FOUND`; the app routes them through signup, where region + terms are
  collected and `/auth/register` carries `appleIdentityToken`.
- The signup path requires the token to contain an email (`APPLE_EMAIL_MISSING`
  otherwise); Apple includes one in every identity token issued with the email scope.
- Error codes the app maps: `APPLE_TOKEN_INVALID`, `APPLE_EMAIL_MISSING`,
  `APPLE_EMAIL_MISMATCH`, plus the shared `ACCOUNT_ALREADY_EXISTS` /
  `ACCOUNT_NOT_FOUND` / `ACCOUNT_NOT_ACTIVE`.

## Verify

Sign in on an iOS build and check the backend log: a rejected token logs
`Apple identity token validation failed` (or `... audience not accepted` — bundle ID
missing from `APPLE_CLIENT_IDS`). A 403 `No account found` on login is expected for a
first-time user: Apple login links existing accounts; signup creates them.

## Known gap (future work)

App Store Review guideline 5.1.1(v): apps offering account deletion must also revoke
the Sign in with Apple token via Apple's REST API (`/auth/revoke`). That server-to-server
call **does** need a Services key (`.p8`, Team ID, Key ID) to mint a client secret.
Account deletion currently does not revoke Apple tokens — add this before the App Store
release that ships Apple sign-in, or be ready to justify it in review.
