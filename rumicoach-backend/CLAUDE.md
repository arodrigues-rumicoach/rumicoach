# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Go backend for **Rumi**, an AI voice life-coaching app. Three parts:
- A REST API (chi, generated from `api/openapi.yaml` via oapi-codegen).
- A real-time voice engine: a WebSocket proxy between the mobile client and the **Gemini Live API** (native audio), driving scripted coaching sessions.
- A **companion messaging channel** (WhatsApp; Telegram-ready): async text/voice-note chat with Rumi plus proactive follow-ups, over Gemini `generateContent` — deliberately separate from the live engine. See `docs/whatsapp-channel.md`.

## Commands

```bash
# Build — do NOT use `go build ./...`: scratch files with duplicate main() live in the
# repo root (read_db.go, test_regex.go, ...) and break it. Build the real packages:
go build ./cmd/server/ ./internal/... ./api/ ./database/

go test ./internal/... ./api/                       # tests
go test ./internal/services/chat/ -run TestName     # single test
go run cmd/server/main.go                            # run server (reads .env, port 8000)
```

Regenerate the API after editing `api/openapi.yaml` (oapi-codegen v2.7.0, no config file — these exact commands reproduce the committed files deterministically):

```bash
oapi-codegen -generate types -package api api/openapi.yaml > api/types.gen.go
oapi-codegen -generate chi-server -package api api/openapi.yaml > api/server.gen.go
```

Known pre-existing test failure: `TestSubmitSessionFeedback` (rating-bounds validation in `internal/handlers/chat.go`) — unrelated to most work.

QA resets user fixtures via `POST /v1/admin/test-setup` (see `internal/handlers/admin.go`, docs page at `/admin/test-data-docs`). The `onboarding_*` step personas seed a mid-**Vision** state (they are named for the old flow); every post-onboarding persona goes through `seedRealUserProfile` + `seedCompletedSession`, which furnish a user exactly as a real one would be after onboarding (vision, focus area, scored wheel, memories in every category plus insights, AI theme/quote picks, typed session history with transcript and the persisted `session_summary`). Commitments accumulate per completed session — onboarding alone already leaves a recurring and a one-time one, and a persona that also did Movement has strictly more, including the overdue one (a user two hours past onboarding can't have missed a deadline yet); the stage is passed as `journeyAfterOnboarding`/`journeyAfterMovement`. Real `communication_sessions` are preserved; only rows whose ID starts with `test-seed-` are replaced, so reruns are idempotent and the growth-journey gates stay consistent. Session timings are what distinguish the personas — the gates read typed session history, so a seeded session must be typed, ended, and long enough to count as done (≥ 5 minutes, or ≥ 45s for the short intro). `seedOpeningPair` seeds both halves — a persona with only the intro would be proposed Vision instead of its own scenario.

## Architecture

### Voice engine (`internal/services/chat/`)

`ChatSession` in `live_api.go` is the core: it proxies client WS ↔ Gemini WS, parses Gemini events, and enforces the session flow. Key mechanics that span multiple files:

- **Per-user active-session registry** (`activeSessions` in `live_api.go`): a new connection for a user terminates the previous session. Clients sometimes double-connect; never allow two live sessions per user.
- **Turn lifecycle**: per-turn flags (`turnSpokeText`, `turnHasToolCall`, `suppressedMarkerThisTurn`, `transitionInjectedThisTurn`, `wheelSetupThisTurn`, `revealsScheduledThisTurn`, `restartFallbackPrompt`) are captured and reset **only** in the TURN_COMPLETE handler. That handler is also where all behavioral safety nets live: the silent-tool "nudge" (wheel-aware variant; delivered via `scheduleSilentToolNudge` after a ~2.5s delay and dropped if the user resumed speaking meanwhile — detected via Gemini `inputTranscription` arrival (`lastUserSpeechUnixNano`), NEVER via client audio frames: the client streams mic audio continuously even in silence, so a frame-based signal cancelled every nudge and left users in dead air after each silent save), missing-tool-call correctives (vision must call `save_ideal_life_vision`; wheel setup must call `set_wheel_of_life_categories`; ending auto-terminates), and the restart-fallback. When the model omits a mandatory tool call the session dies in silence — every mandatory-tool step needs a TURN_COMPLETE safety net.
- **Restarts**: Gemini system instruction + tools are fixed per connection; changing them requires a reconnect. Hard restarts happen only at the Wheel of Life boundaries (`NeedsRestart`) and via the 7-minute `restart_session_with_summary` flow. Post-restart directives are injected at setupComplete with `languageContinuityReminder` appended and a 1s `injectSilence` gap when the model spoke pre-restart (otherwise audio glues). **Never gate a tool's declaration differently from its trigger** — a prompt ordering the model to call an undeclared tool yields Gemini's "Invalid function call" and a dead session.
- **Turn detection**: the setup carries `realtimeInputConfig.automaticActivityDetection` (`END_SENSITIVITY_LOW` + `silenceDurationMs`, from `GEMINI_TURN_SILENCE_MS` / `GEMINI_REFLECTIVE_TURN_SILENCE_MS`). The provider default is tuned for quick back-and-forth and talks over anyone pausing to think — fatal in exercises built on reflection (QA: Rumi cut a user off with the very "take your time" cue meant to give him room). The reflective value applies in `VISION_IDEAL_LIFE` and `VISION_WHEEL_OF_LIFE`; setup is rebuilt per connection, so the wheel restart picks it up. `0` restores the provider default, so an unsupported field can never break every session.
- **Session resumption**: Gemini handles are persisted (`latest_session_handle`) and resumed only within 10 seconds; persistence stops once `clientGone` (the disconnect flow re-persisting handles caused "ghost resumes").
- **Client-disconnect flow**: sets `clientGone`, then runs closing housekeeping on the still-open Gemini connection (schedule-notifications prompt). Nudges must not fire after `clientGone`; `schedule_notifications` must be declared on **every** connection because this flow can run at any phase. Scheduled notifications are channel-agnostic (`notifications` table): the dispatcher in `internal/services/notification/dispatcher.go` picks the delivery channel at send time — active messaging channel first, FCM push only as last resort, exactly one channel per notification.
- **Control markers** (see `docs/control-markers.md`): the model emits silent glyph pairs — `◆▣`/`◆▤` open the memories/session screens. Reveals are scheduled **at parse time** from an estimated speech rate (`estimatedSpeechCharsPerSecond` × text before the marker, relative to the turn's audio start). Do NOT defer them to TURN_COMPLETE: Gemini paces the audio stream at ≈ realtime, so TURN_COMPLETE arrives when the speech has effectively been heard already, and a deferred reveal always fires at the very end of the turn (QA bug). The ONE deliberate exception is the `◆▦` session-summary reveal (`pendingSummaryReveal`): the marker opens the synthesis turn, so parse-time scheduling flashed the panel the instant Rumi started speaking — reading + listening at once was QA-rejected — and end-of-turn is exactly when the user should read it. For the same reason `session_terminated` is held back by a text-length estimate of the turn's remaining speech (`estimateSpeechRemainingSecs`, stashed in `pendingShutdownDelaySecs` before dispatch) so the goodbye isn't cut off mid-sentence — on a turn ending in `terminate_session`, the actual audio bytes typically haven't started arriving at all yet by the time the tool call is processed, so byte-based duration accounting (`turnAudioDuration`/`turnAudioStartTime`) can't be trusted there. Pause markers (`●`) are parsed but currently disabled in prompts. Data-bearing screens (Wheel of Life) are NEVER opened by marker/`show_screen` — only by the tool that carries their data (`set_wheel_of_life_categories`).
- **Transcripts**: `logHistory` builds the saved session transcript; `ai_transcript` server→client payloads are deliberately excluded (the `[AI]` entries already carry the text).

### Sessions (`internal/services/chat/session/`)

Registry pattern: `api.SessionType` → `session.Session` implementation (`onboarding/`, `vision/`, `movement/`, `values/`, `checkin/`, `energy/`, `decisions/`, `beliefs/`). A new session is not live until it is added to `registry.go` — `registry_test.go` is what catches a missing entry. Each session owns its prompts (`Instructions(state, ctx)`), persona, transitions (`NextOnCompleteTask`), restart boundaries, and — importantly — its **tool list** (`ToolNames(state)`). The runtime adds only `save_memory`, `request_recommendations`, `schedule_notifications`, and (always) `restart_session_with_summary`; everything else must be listed by the session. The Vision session's opening stretch (ideal-life→wheel) deliberately excludes `show_screen`/`save_session_insight`.

The opening arc is two sessions, and the app starts the intro explicitly right after account creation (it is not journey-gated). **`onboarding`** is the intro alone — greeting, the registration details Rumi collects in conversation (country/date of birth/gender via `save_profile_details`, one question at a time), privacy/memories screen, roadmap — a single `ONBOARDING_INTRO` state. Signup owns what the intro must NOT ask: the **data region** is chosen in the app before the account is provisioned, because it decides which regional database the profile is created in and there is no cross-plane migration; **coach gender/voice** likewise stay in the app, since the session needs a voice to speak with. It ends by asking whether to begin the first exercise now: yes calls `start_planned_session` (restart straight into Vision), no calls `terminate_session`. Either way the user lands on `VISION_IDEAL_LIFE`, so someone who declines is still routed to Vision (and still free) when they return — `handleTerminateSession` special-cases this instead of parking them at `CHECKIN`. **`session_vision`** is the multi-state one: `VISION_IDEAL_LIFE → VISION_WHEEL_OF_LIFE → VISION_METAPHOR → VISION_EMOTIONAL_CLOSING → VISION_ENDING_SESSION`, ending in the `CHECKIN` resting state (persisted on `users.state`, whose default is now `VISION_IDEAL_LIFE` — the resting state *after* the app-driven intro). Because that default is also where a user who declined the exercise is parked, `VISION_IDEAL_LIFE` cannot prove the intro happened — which is why `ProposeSession` and `resolveSessionType` both ask the **artifacts** (profile details set, `ideal_life_vision_set_at` non-NULL) rather than the state. At `CHECKIN` **with the opening pair finished**, a client-requested `session_vision`/`onboarding` resolves to `checkin` (it is never revisited; honoring the stale type skipped the planned-session offer, mistyped the history row, and keyed the summary builder wrong — QA), while a later deep session the app launches directly is honored. At `CHECKIN` with the pair **unfinished** — where `terminate_session` parks a Vision session the user cut short — everything resolves to `session_vision` instead: the journey proposes Vision to those users, so resolving them to a check-in made the app offer one session and the server run another, for free. The `VISION_*` states carried an `ONBOARDING_` prefix before the split; the prefix had to change because `IsOnboarding()` keys off it (`database/db.go` backfills stored rows). States advance through tools dispatched in `tools.go` (`complete_current_task`, or dedicated tools like `save_ideal_life_vision` / `save_focus` that advance implicitly). Other sessions are single-prompt conversations ended by `terminate_session`.

### Prompts & language (critical)

- **All prompts and code are written in English**, but users speak any language (`preferred_language`, e.g. pt-PT). The LANGUAGE directive in `system_prompt.go` declares scripts to be **templates translated at runtime** — "deliver this EXACT script" means exact meaning in the user's language, never literal English.
- **Never** branch on English phrase-matching of AI/user text (e.g. `strings.Contains(lastAI, "ready to save")`) — it silently breaks in other languages. Several such guards were removed as bugs; one legacy non-blocking assist remains in the emotional-closing text path.
- Tool arguments that echo stored values (e.g. `update_wheel_of_life` category names) must use the stored, translated names — error messages list valid values so the model can self-correct.
- The persona lives in `session/persona.go` (`DefaultPersona`, used by every later session) and is duplicated in `session/first_session_persona.go` (`FirstSessionPersona`, shared by the onboarding intro and Vision — one continuous first meeting, so they must not sound like different coaches); behavioral rules edited in one must be mirrored in the other.

### Growth journey (`internal/services/journey/`)

`deepSequence`: onboarding → vision → movement → values → energy → decisions → beliefs → identity → acceptance → priorities. The first two are the **opening pair**, done once and never revisited when the journey cycles (`deepSequence[2:]`), and both are **free** until they have produced their artifacts — see the Minutes balance section; the decision is always server-side, never the client-supplied `session_type`. `ProposeSession` routes on those same artifacts (profile details set, `ideal_life_vision_set_at` non-NULL) rather than on `users.state`, so the journey and the billing rule cannot disagree about when the introduction is over. Otherwise gates are **calendar days** at local midnight (the hour a session happened never matters; timezone from the request) — **Vision unlocks immediately after the intro** (no overnight wait; the two are one first meeting), Movement the day after Vision, each later deep session 5 days after the last deep session (check-ins never count), else the daily `checkin`. A session only counts as done past a duration threshold: 5 minutes normally, but **45s for the intro**, which is short by design — holding it to the full threshold would loop users through onboarding forever. Once the first pass is complete the journey **cycles**: the least-recently-done deep session comes around again, 5 days after the last one — `NextDeepSession` (the `nextSession`/`availableAt` preview on `/journey`) is therefore nil only inside the opening pair, never "journey over". Both the intro and the check-in are gateways: `start_planned_session` switches the live session type via restart (the intro always hands to Vision; the check-in resolves `PlannedSessionForToday`), and **rolls the `communication_sessions` row over** (`rolloverSessionDB` in live_api.go): the gates read typed, ended rows, so one connection must leave one row per session actually held — the ended half is finalized like Cleanup's final row (transcript, duration, debit when billable, background recap/review) and a fresh row typed as the planned session is opened; a single row spanning both halves left the second half invisible to the gates. See `docs/sessions.md`.

End-of-session, the model also picks a **quote category and Journey-screen theme** for the coming days (`quote_category`/`theme` args on `schedule_notifications`, validated via `quote.NormalizeCategory`/`models.NormalizeJourneyTheme`, stored as `users.journey_quote_category`/`journey_theme` — never overwriting the user's manual `users.theme`). `GET /journey` filters the daily quote by that category and returns `theme` (AI pick → `users.theme` → `waterfall`). Theme slugs live in `models.JourneyThemes` and must match the frontend's keys.

### Companion channel (`internal/services/messaging/` + `internal/services/companion/`)

WhatsApp chat with Rumi (text + voice notes both ways) and proactive follow-ups. Key invariants:

- **Separate pipeline from the live engine**: stateless per turn — system prompt + last 30 messages (≤72h) from `channel_messages` → Gemini `generateContent` with a tiny tool set (`save_memory` only). Long-term continuity comes from `user_memories`, NOT the raw log (which can be purged — `COMPANION_EPHEMERAL_HISTORY` deletes a conversation after N hours of inactivity, default 6). The companion system prompt (`companion/prompt.go`) is standalone; it must never inherit voice-session directives (glyphs, audio protocol, session states).
- **Gemini 3 tool loop**: function-call parts carry a `thoughtSignature` that MUST be echoed back when replaying the model turn, or the API 400s (`companion.Part` round-trips it).
- **Webhook** (`internal/handlers/whatsapp_webhook.go`) lives OUTSIDE `/v1` and self-authenticates via Meta's `X-Hub-Signature-256` HMAC; it 200-acks immediately and processes async. Meta redelivers events — every inbound insert dedupes via `ON CONFLICT (provider_message_id) DO NOTHING` (zero rows affected = drop).
- **Channel abstraction**: `messaging.Channel` interface; per-region Meta app/number (one per data plane, no cross-plane forwarding). Missing credentials in development → mock channel that logs sends.
- **Proactive messages** honor WhatsApp's 24h customer-service window (`ChannelBinding.LastInboundAt`): free-form inside, pre-approved template (`WHATSAPP_TEMPLATE_REENGAGE`) outside. The dispatcher (started from `main.go`) drains `channel_follow_ups` with `FOR UPDATE SKIP LOCKED` — replica-safe; daily-nudge enqueueing is serialized with a pg advisory lock. **Anti-repetition memory**: every delivered proactive message's text is stamped on its follow-up row (`sent_text`; chat-composed scheduled notifications insert a log-only, already-drained row of kind `scheduled_notification`), and `recentProactiveBlock` replays the last few into each proactive directive. It deliberately reads `channel_follow_ups`, never conversation history — the ephemeral purge erases `channel_messages` after a few quiet hours, and quiet users are exactly who proactive messages go to. Because `sent_text` is delivered copy, the 30-day follow-up sweep and chat-scope erasure are privacy bounds, not just hygiene.
- Account linking: `POST /v1/me/channels/whatsapp/link` issues a `RUMI-XXXXXX` code (15-min TTL) the user sends via a wa.me deep link. Voice-note replies need **ffmpeg** (in the Docker image); TTS falls back to text without it.
- **Usage metering**: token spend goes to `ai_usage_records` (via `recordUsage`), message charges to `balance_transactions` (via `deliverReply`). The old per-message event ledger, `channel_usage_records`, is **legacy-orphaned like `goals`** — model deleted, nothing writes or reads it, existing rows purged on the QA account reset via guarded raw SQL. There is consequently no durable "messages delivered" count anymore; if one is ever needed again, it must be a new decision, not a revival. It exists because `channel_messages` is erasable three ways (retention expiry, ephemeral purge, `scope=chat` deletion), so counting must never derive from it; it follows the `balance_transactions` rule and is NEVER deleted by any erasure. Count "messages sent" as outbound rows with status `sent`. Its token columns are **deprecated and no longer written** — spend moved to `ai_usage_records` (see below) so it can be summed against sessions; the columns keep the history already in them. `Usage` is still accumulated across **every** Gemini call in a turn (tool-loop iterations + STT + TTS — the final response alone undercounts tool turns) and handed to `recordUsage`, which writes both rows. Every send funnels through `recordOutbound`, every generated turn through `runChatTurn`; new paths must keep it that way.

### Focus area & actions

Goals were removed: the user's commitment is `users.focus_area` (set by `save_focus` in onboarding METAPHOR, exposed on `GET /me` as `focusArea`) plus `Action` rows (`actions` table; `origin` = `plan`|`manual`|`behavior`, no goal link — the legacy `goals` table still exists in the DB but is orphaned, purged on account deletion via raw SQL). Per-day completion of recurring actions lives in the `DailyJourney.Actions` JSONB snapshot (`DailyAction`, column `actions`), recomputed via the single source of truth `models.ActiveActionsForDate`. `GET /journey` returns a flat `actions` list; REST CRUD is `/actions` (+ `PUT /journey/actions/{id}`). Chat writes plans via `update_action_plan`/`save_actions` (origin=plan) and `add_action` (manual). See `docs/api-goals-tasks.md`.

### Minutes balance (`internal/services/balance/`)

The minutes bank for the upcoming subscriptions/top-ups: `users.balance_seconds` (seconds, may go negative) plus the immutable `balance_transactions` ledger (signed `amount_seconds`, `balance_after`, unique `session_id` index = hard guarantee against double-debiting a session). Invariants:

- **Every mutation goes through the balance package** (`Credit`/`CreditPurchase`/`DebitSession`/`DebitMessage`/`RecordFreeSession`): one DB transaction, `SELECT ... FOR UPDATE` on the users row, single-column update of `balance_seconds`, ledger insert. This is ORM-enforced, not comment-enforced: the model marks `balance_seconds` `<-:false`, so full-row `Save`s skip the column on their own (no `Omit` needed) and a struct write can never clobber a concurrent debit. The only writers are two raw-SQL statements: the ledger's `apply()` and the QA account reset, which zeroes the column in the same transaction that deletes the ledger. The invariant `balance_seconds = SUM(amount_seconds)` (= `balance_after` of the newest row) holds for everything written through this code; verify against pre-ledger history with a one-off reconciliation query before trusting it globally.
- **Debit at session end** in `Cleanup()` (live_api.go), right after `EndTime` is saved — elapsed whole seconds, log-and-continue on failure (billing must never break session close). **The introductory sessions are free**: `balanceExempt` is captured once at session start from `balance.FreeSessionAvailable(userID, sessionType)`, and held for the whole session (the artifacts it reads are written mid-session).
- **What counts as free** (`balance.FreeSessionAvailable`): the session type is `onboarding` or `session_vision` — the SERVER-resolved type, never the client-supplied one — **and** `balance.OpeningPairUnfinished`, i.e. the opening pair has not yet produced what it exists to produce: the profile details the intro collects (`NeedsProfileDetails`) and `users.ideal_life_vision_set_at`. Backstopped by `FreeSessionCap` (10 sessions passing `SessionCountsAsDone`, un-scoped by journey reset) so a user who never finishes Vision cannot talk indefinitely for free. Two earlier rules are documented as tombstones in `internal/models/user.go` and must not come back: reading `users.state` (defaults to a Vision value, so it exempted everybody who never finished) and counting session rows (the row is written at connect, so a five-second drop spent a free session and paywalled a half-onboarded user).
- **WS pre-flight** (`api/routes/chat.go`, POST-upgrade): users past their introductory sessions holding less than `balance.MinimumStartSeconds` (**60s** — a session that dies right after the greeting is worse than a paywall, and the end-of-session debit overdraws anyway) get an `{"type":"error","code":"INSUFFICIENT_BALANCE"}` frame and close code **4402**. Deliberately after `upgrader.Upgrade`: a handshake refused with an HTTP status is invisible to every WebSocket client, so the app could only show "connection failed" unless it duplicated the billing rule against `/me` — which it did, and the copies drifted into paywalling users mid-onboarding. The app now runs no client-side gate at all; it opens the socket and reacts (`WS_CLOSE_INSUFFICIENT_BALANCE` in the app's `SessionContext`). The pre-flight asks the account-level `OpeningPairUnfinished` because the session type is not resolved yet; `resolveSessionType` guarantees an unfinished opening pair is always routed to onboarding/Vision, so the two cannot disagree. Behind `BALANCE_ENFORCED` (default **true**); debits/ledger run regardless. DB errors fail open.
- **Companion replies are charged, and only replies**: applied in `deliverReply` when `currentMsg != nil` — the user's message being answered. Each side is priced for what it was (`companion.Spend.ChargeSeconds`): **audio by its real length, both received and sent**; **text at the flat `balance.MessageCostSeconds` (5s), once, on the reply**. So voice→voice pays for both recordings, voice→text pays what the user spoke plus the flat fee (the ordinary case when the integration's `ReplyMode` is `text`, not just a TTS fallback), text→voice pays for the recording alone, and text→text pays 5s. `ReplyMode` `auto` mirrors what the user sent; `text`/`audio` pin the reply regardless. Durations: outbound is exact from the PCM byte count (Gemini TTS is s16le/24kHz/mono); inbound is probed with `ffprobe` because neither webhook carries one, and a failed probe charges **zero** for that side rather than guessing — logged at Error, since a missing ffprobe would silently make every voice note free. Both truncate to whole seconds, like the session debit. Everything we send on our own initiative (proactive nudges, re-engagement templates, the daily-cap and transcription-failure notices) passes `nil` there and is free, because billing someone for a message they did not ask for is indefensible. Keyed on the INBOUND message id (`reference_id = "message:<id>"`), so a redelivered inbound that slips past the webhook dedupe cannot be charged twice; a duplicate returns `ErrDuplicateReference` and is treated as already-charged. Charged only after the send succeeded, and log-and-continue like the session debit. `GET /me/usage` lists **only charged replies**, count and seconds both from these debits — it is a bill, and what we send unprompted is not on it. It no longer reads `channel_usage_records` at all, which leaves that table with **no readers** (see the Companion channel section).
- **A free session still writes a ledger row**: `balance.RecordFreeSession` inserts a zero-amount `session_free` row (both at Cleanup and at the handover). It moves no balance, so `balance_seconds = SUM(amount_seconds)` holds; it exists because the ABSENCE of a debit is ambiguous — it could equally be a debit that failed (log-and-continue) or a sub-second session. `GET /me/usage` shows those entries with `free: true` and the session's real duration (read from `communication_sessions`, the one place this feed otherwise refuses to look: the ban is about billing sources, and a duration for display survives redaction). They add to `sessionCount` and `freeSessionSeconds`, never to `sessionSeconds` or `totalSeconds`, so "what you spent" stays honest while the history still accounts for every session the user had.
- **`inFirstJourney` on `GET /me`** is `OpeningPairUnfinished` — informational, for display and for shipped app builds that still pre-empt. Nothing may gate on it.
- Crediting: **RevenueCat webhook** `POST /v1/webhooks/revenuecat` (see `docs/revenuecat.md`) — self-authenticated via the exact `Authorization` header value (`REVENUECAT_WEBHOOK_AUTH`), maps products to minutes via `REVENUECAT_PRODUCT_MINUTES`, credits through `balance.CreditPurchase` keyed by `reference_id = "revenuecat:<event id>"` (unique index — redeliveries can't double-credit, the credit-side mirror of the `session_id` guarantee). Unknown product → 500 so RevenueCat retries until the mapping ships; unknown user → 200 drop (the other regional plane owns them; one webhook per plane, no forwarding). **Refunds claw the grant back**: there is no REFUND event type — a refund arrives as `CANCELLATION` with `cancel_reason: CUSTOMER_SUPPORT` (any other reason is an auto-renew change and keeps granted minutes) — and `balance.RefundPurchase` debits the product's full mapped amount, negative balance allowed, deduped on the refund event's own id (namespaced `revenuecat:refund:tx:` in the transaction-id fallback, since a refund shares its transaction_id with the purchase it undoes). Plus `POST /v1/admin/users/{id}/credits` (admin-gated manual credit). Balance is exposed on `GET /v1/me` (`balanceSeconds`); history on `GET /v1/me/transactions`. QA test-setup preserves balance/ledger, like `communication_sessions`.

### AI cost ledger (`internal/services/aiusage/`)

`ai_usage_records` is **the only table that stores token counts**, for every part of the product — live voice sessions, companion turns, session recaps, QA reviews, the recommendation agent. Tokens plus what they cost us, never content. Written through `aiusage.Write`, which is log-and-continue and computes the cost itself so no call site can invent one.

`communication_sessions`, `channel_messages` and `channel_usage_records` all used to carry their own token columns; none do now (the DB columns remain with their history, unread and unwritten). A voice session counts its tokens in memory (`ChatSession.tokens`, reset by `InitDB` so each half of a handover accounts for itself) and writes them here at Cleanup — or at `rolloverSessionDB` for the half that ends mid-connection. The admin dashboard reads cost and tokens from here too (`sessionCostUSDSQL`), rather than the hard-coded pricing arithmetic it used to carry in SQL — which covered only the live session, so every figure on it silently omitted the recap, review and recommendations each session also pays for.

Two ledgers, two questions — do not conflate them:

| | Question | Unit |
|---|---|---|
| `balance_transactions` | what the USER pays and holds | signed seconds (0 for a free session) |
| `ai_usage_records` | what serving it COST US | tokens → micro-dollars |

A charged operation writes two rows (cost here, price in `balance_transactions`); a failed call writes only here, having burned tokens and produced nothing to charge for. Rows survive every content erasure; only full account deletion removes them.

**Prices live in `aiusage/prices.go`** — checked in, not configured: a price is a fact about a model, it changes rarely, and it should move through review like anything else billing depends on. Read from https://ai.google.dev/gemini-api/docs/pricing (paid tier), with the date and source in the file header. Rates are **per modality** (input text/audio, output text/audio) because the Live model charges audio output $12.00 against $4.50 for text and a voice session is nearly all audio — a single output rate understates it ~2.7x. A model with no entry records its tokens with a NULL cost rather than a guess; `PriceTableVersion` is stamped on every priced row, so bump it when a price changes and old rows stay explainable. Money is integer micro-dollars throughout — never a float.

Adding or switching a model means adding its price. Guard tests in `companion` and `chat` (`pricing_guard_test.go`) fail when a default model has no entry — they live in those packages because only they can see what the defaults are.

**One event can span several models.** Answering a voice note runs transcription, the chat turn and speech synthesis on three models at three prices ($20.00/M output for TTS against $9.00 for chat), so a row carries the primary model plus `stt_*` and `tts_*` column groups, each with the model that earned it. `CostOf` prices all three and sums; if ANY model carrying tokens is unpriced it records NULL rather than a partial sum, because an understatement reads as fact while a NULL is visibly incomplete and repriceable. In the companion this is `companion.Spend` (`Chat`/`STT`/`TTS`), which replaced a single accumulator that merged the three and left everything priced as chat.

Known gap, documented at its site: `gemini-3.1-pro-preview`'s >200k-token tier is not modelled (the recommendation agent's prompts are nowhere near it).

### SSO identity & account linking (`internal/handlers/auth.go`, `apple.go`)

One account, several ways in. The credentials live on `Identity` in the auth database (`google_id`, `apple_id`, `email`); every provider token is reduced to an `ssoToken` (subject + email + `email_verified` + Apple's `is_private_email`) and nothing else about the request may reach an account lookup — the `email`/`name` the app sends alongside an Apple token are informational, and linking by them would let any Apple user attach their credential to an arbitrary account.

- **Lookup order is provider id, then email — not the reverse.** The `sub` is the stable key; emails change (`PUT /auth/me/identifier`), so an email-first lookup can send a user with a valid credential into a different account. The email is the fallback that lets a credential attach itself to an account created another way, which is what makes Google→Apple (and Apple→Google) work at all.
- **Only an email the provider vouches for may find an account** (`ssoToken.linkableEmail`). Without that gate, an IdP that lets anyone claim an unverified address is an account-takeover path. A **missing** `email_verified` claim counts as verified on purpose: both providers always send it, so its absence means the payload changed shape, and locking every user out is worse than the attack, which needs an explicit false. An explicit false is refused at signup too — an account keyed on an address nobody vouches for squats on the real owner's mailbox.
- **"Hide My Email" cannot be solved by any lookup order.** The token carries a per-app `@privaterelay.appleid.com` address, so an account created with Google can never be matched by email. `POST /v1/auth/me/link/apple` (`LinkAppleAccount`) is the only way in: authenticated, so the account is proven by the bearer token and no email match is needed or attempted. `AppleLogin` reports that dead end as `APPLE_PRIVATE_EMAIL_UNLINKED`, distinct from `ACCOUNT_NOT_FOUND`, because the remedy is different.
- **`POST /auth/verifications/sso` is a signup pre-check, not a verdict.** `EMAIL_ALREADY_EXISTS`/`ACCOUNT_ALREADY_EXISTS` mean "log in with this same token instead" — the app falls back to `/auth/google` / `/auth/apple`, which link the credential to the account they find. The status codes stay as they are because shipped builds depend on them.
- Credentials are attached with `linkProviderID` (single-column update), never a full-row `Save` that would write back a refresh-token hash a concurrent login has rotated.

### REST layer gotchas

- **Auth is a hand-maintained path allowlist** — `selectiveAuth` in `cmd/server/main.go`. A new `/v1/...` route is unauthenticated (handlers then 401 on missing userID) until its prefix is added there. The OpenAPI `security` sections are not enforced by the generated code.
- Migrations: GORM AutoMigrate plus idempotent custom pre-migrations in `database/db.go` (e.g. `tasks` → `actions` table rename, origin `goal` → `plan`).

## Working practices learned in this repo

- Debugging flows: QA supplies transcript logs (`test_logs/`) in the `[timestamp] [ROLE]` format; server logs carry per-window inbound-audio stats (`Client audio inbound window`) to separate client vs backend vs Gemini failures.
- When editing files containing the marker glyphs (◆●▣▤▁–█), do not use `perl -CSD` (it double-encodes UTF-8); use the Edit tool or Python byte-level replacement.
- LSP diagnostics in this repo frequently show stale `api.SessionType undefined` errors after codegen; trust `go build`.
- Model-behavior bugs (skipped tool calls, leaked markers, English reversion) are fixed with **both** a prompt hardening **and** a server-side guard/corrective — prompts alone don't reliably stick.
